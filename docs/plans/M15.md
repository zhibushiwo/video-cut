## 20.1 三条硬约束（决定了整个设计）

### 20.1.1 后端路径现成，且正好是全程无损 —— 但只有 copy 一条路

`commands/pipeline.rs::plan_items` 的**规则 A**：所有片段无裁剪 + 目标朝向一致 → **全部 copy**（每段一条 `-ss/-t + -display_rotation` copy 命令）→ concat demuxer 拼接成一个文件。本批的 items 全部来自**同一个源**、无旋转增量、无裁剪 ⇒ 目标朝向天然一致 ⇒ 命中规则 A ⇒ **秒级、无损、单文件**。

反过来说：`PipelineItem` **没有"强制重编码"字段**，`plan_items` 只要"无裁剪 + 朝向一致"就一律 copy——**前端无从要求帧级精确**。所以 CAND-020 原文 ④ 的"强制精确重编码"选项在现有契约下**不可达**，本批裁决为"UI 明示延伸范围"（精确边界另立候选 `CAND-022`，见 §20.7 `D2`）。

### 20.1.2 copy 的真实语义是"窗口整体前移"

`ffmpeg/command.rs::pipeline_copy_args` 是 `-ss fmt_seek(start)` **在 `-i` 前**、`-t fmt_sec(dur)` 在后，且 `dur = end − start`。ffmpeg 把 `-ss` 落到 **≤ start 的最近关键帧**，于是实际输出窗口是：

```text
[kf(start), kf(start) + (end − start)]
```

即整个窗口**前移** `δ = start − kf(start)`：

- 头部**残留** δ 秒"本该删掉"的内容（垃圾没删干净）；
- 尾部**被削掉** δ 秒；若这是最后一段，**成品结尾直接少 δ 秒**。

（这正是 `BUG-007` 的同族现象——提取式下表现为"产物比界面承诺长"；这里表现为"删不干净 + 啃结尾"。）

### 20.1.3 ⇒ 吸附方向必须反向：向上对齐，而不是向下

要让垃圾**一点不残留**，必须让输出窗口的起点 ≥ 删除区间的终点 `b`。由于 ffmpeg 取的是"≤ start 的最近关键帧"，唯一办法是**把保留段的起点直接设成关键帧**：

```text
s' = min{ kf | kf ≥ b }        （≥ 删除终点的最近关键帧；不存在则取片尾）
```

这样 `δ = 0`，输出窗口 = `[s', end]`：**删除区间的起点精确、终点向后延伸到一个关键帧**（多删 ≤ 1 个 GOP，宁多删、不残留）。

> **与提取式的方向正好相反**：提取式的入点用 `utils/time.ts::realCutStart`（**向下**取 ≤ 入点的关键帧，宁可多留 —— `NFR-004`/`BUG-009` 的"实际落点"明示）；本批的终点对齐必须**向上**。两个谓词**必须分开命名、不得混用**（`nextKeyframeAtOrAfter` vs `realCutStart`），并在代码注释里互相指认。

**举例**（60s 源、关键帧每 2s）：标记删除 `[10.0, 19.3]` → `s' = 20.0` → 实际删除 `[10.0, 20.0]`（延伸 0.7s），保留段 `[0,10] + [20,60]`，成品 50s，全程 copy。若标记终点恰落在关键帧上（`[10.0, 18.0]`）→ 延伸 0，完全精确。

## 20.2 派生链（`M15-1`，纯函数 + Vitest）

新增 `utils/removal.ts`（与 `utils/crop.ts` 同族：纯计算、可单测、不含 IPC），并在 `utils/time.ts` 里紧挨 `realCutStart` 增 `nextKeyframeAtOrAfter`。

```ts
export interface Interval { start: number; end: number }   // 派生链内部的秒区间（≠ 契约层 Segment{startSec,endSec}）

export type RemovalBlockReason =
  | "no-marks"        // 还没标记任何区间（不是错误，只是导出按钮不可用）
  | "no-keyframes"    // 关键帧索引未就绪/为空——无损删除的边界定不了
  | "nothing-left";   // 全删光

export interface RemovalPlan {
  /** 实际删除区间（已含向上吸附带来的延伸），供时间轴 warn 色带渲染 */
  removals: Interval[];
  /** 保留区间 = 下发给 `pipeline` 的每段 `segment` */
  keeps: Interval[];
  /** 每个保留段头部的额外删除量（秒；与 `keeps` 同序，首段恒 0）——UI 明示"延伸 x.xs"（NFR-004 口径） */
  extends: number[];
  /** 成品总时长（= Σ 保留段时长） */
  totalSec: number;
  /** 非 null 时禁用导出并显示原因 */
  blocked: RemovalBlockReason | null;
}

/** 入口入参（`keyframes = null` 表示索引未就绪） */
export interface PlanRemovalArgs {
  marks: readonly Interval[];
  durationSec: number;
  keyframes: readonly number[] | null;
  minKeepSec: number;   // = MIN_SEG_DURATION_SEC（0.05s，与后端 valid_segment_span 同源）
  fps: number;          // 仅在 fps 已知时用于 1 帧下限，同 utils/undo/commands.ts::minSegSec 口径
}

/** 入口：标记区间 + 时长 + 关键帧 → 导出计划 */
export function planRemoval(args: PlanRemovalArgs): RemovalPlan;
```

内部步骤（每一步都单独导出，便于逐条单测）：

| # | 函数 | 规则 |
| --- | --- | --- |
| 1 | `normalizeRemovals(raw, duration)` | 裁到 `[0, duration]`、丢弃**非有限值与**长度 ≤ 0、按起点排序、**合并重叠与相邻**（相邻容差用 `1e-9`，只吸收浮点末位差、不吞真实间隔） |
| 2 | `complementIntervals(blocks, duration)` | 对 `[0, duration]` 求补集（丢弃空段）。**两处复用同一关系、方向相反**：步骤 2 是"标记 → 保留段"，收尾是"保留段 → 实际删除区间"（把吸附延伸与碎片吸收一并算进 warn 色带） |
| 3 | `nextKeyframeAtOrAfter(t, keyframes)` | 二分找 `≥ t` 的最近关键帧；不存在返回 `null`（调用方按片尾处理 ⇒ 该段作废） |
| 4 | 对齐 | 第 `i` 个保留段紧跟第 `i-1` 个删除区间 ⇒ 起点 = `nextKeyframeAtOrAfter(前一个删除区间的终点) ?? duration`（**起点为 0 的首段天然落在 0 号关键帧上，不动**）；延伸量 = `对齐后的起点 − 吸附前该段起点` |
| 5 | **不动点迭代** | 步骤 4 会把保留段缩短到下限以下、甚至归零（关键帧稀疏时）⇒ **对合格保留段求补集**即得新的删除区间，回到步骤 2 重算，直到 `keeps` 稳定（数量单调不增，必然收敛） |

**门禁判定**（优先级从高到低，UI 文案按此顺序给）：`marks` 为空 → `no-marks`；`keyframes` 为 null/空 → `no-keyframes`；`keeps` 为空或全部低于下限 → `nothing-left`。

**为什么必须做不动点迭代**：吸附是"缩小保留段"的操作，会造出新的碎片/空段；只做一轮就会把'越过下限的保留段'直接下发给后端，被 `commands/mod.rs::valid_segment_span`（`end − start > 0.05 − 1e-6`）整单拒绝。**这条是"看似线性的派生链其实是个不动点问题"的关键**，实施时必须有对应用例（关键帧稀疏 + 两个删除区间夹一个极短保留段）。

**实现裁决（`M15-1` 落地时定，2026-09-28）**：

- **有效下限** = `max(传入的 minKeepSec, minSegSec(fps))` = `max(0.05s, 1 帧)`——与命令层切割/修剪下限、导出映射阈值、后端 `valid_segment_span` 同源（`BUG-012` 裁决），并留 `1e-6` 容差吸收"恰好钳到下限"的末位差；
- **关键帧未就绪时不给保留段与时长**（`keeps = []`、`totalSec = 0`，`removals` = 归一化标记仅供色带预览）——避免在索引到位前展示"未吸附"的假精确；
- **超限分支不引日志**：迭代上限（`initial.length + 1`）只作防御，命中即返回 `nothing-left`；纯函数层不依赖 `logger`（保持"可单测、无 IPC"的定位）。实测第 2 轮即为确认轮——丢弃的段不改变其余段的吸附基准（吸附只看"前一段删除区间的终点"，并段不改变该终点）。

## 20.3 剪切页「删除」模式（`M15-2`）

**模式切换**：剪切页工具栏加一个「**提取片段 / 删除片段**」分段控件，**默认提取**（现有行为一字不改）。切到删除模式时**隐藏**「极速 / 精确」组——本批删除只做无损，留着会误导；页脚模式徽标固定「无损」。

**布局沿用现有分栏**（预览 / 时间轴 / 字段行 / 列表），不新开页面：复用 `VideoPlayer`、`Timeline`、关键帧扫描、代理预览、输出目录、任务系统——独立轻量页要把这些再抄一遍，工作台过重（`D1`）。

**标记交互（MVP，`D3`）**：

1. 双手柄选区（`I`/`O` 快捷键 + 「开始=当前帧」「结束=当前帧」按钮，后者随 `M14-4` 落地——**这两条天然配套**）→ 点「**标记为删除**」加入删除列表；
2. **删除列表**每行：`#序号 · 标记 [a,b] · 实际删除 [a,K] · 延伸 x.xs · 时长 · ✕`；`Delete`/`Backspace` 删最后一条（与提取式的既有键位对称）；点击行 → seek 到该区间起点；
3. **时间轴**：删除区间画 warn 色带，实际延伸部分用 warn 虚线标示（`Timeline` 新增**可选** prop `removalMarks?: RemovalMark[]`（`{start, end, actualEnd}`）做只读渲染，不传即旧行为），色带 `pointer-events-none`、不拦截轨道的点击 seek——**沿用 extract 侧 `realStart` 那套"实际落点"明示手法**（`NFR-004`）；
4. **保留段汇总**：`成品 = N 段 · 总时长 m:ss`，折行列出每段起止（只读，不可编辑）；
5. **不可撤销披露**：删除列表是普通 state，**不入撤销栈**（剪切页没有撤销栈，与提取列表同口径）；逐条 ✕ + 「重置」（`M14-2`）是回退手段；
6. **与「重置 / 换素材」的衔接**：`M14-2` 的重置必须**同时清空删除列表与提取列表**（本批落地后两者并存，见 `D5`）；该要求在 [plans/M14.md](./M14.md) §19.2 同批回填。

**门禁与提示**（全部来自 `RemovalPlan.blocked`）：

| 状态 | UI |
| --- | --- |
| 还没标记 | 导出按钮禁用，提示「先在时间轴上选区间 → 标记为删除」 |
| 关键帧索引未就绪 | 导出按钮禁用 + 「正在扫描关键帧…（无损删除需要它来确定边界）」 |
| 全删光 | 导出按钮禁用 + 「至少要保留一段」 |

**明确不做（防反复）**：时间轴上直接拖拽已标记区间的边界（需要 `Timeline` 支持多区间命中与第三类拖拽，`D3` 留 P2）；播放时自动跳过删除区间（`D8` 归 `M12-2`——渲染即预览生效后"预览=真成品"，跳过语义自然消失，现在做等于白做一套走带逻辑）。

**落地记录（`M15-2`，2026-09-28）**：

- `pages/Cut`：新增 `CutTab = "extract" | "remove"`（默认提取）与 `marks` state；「提取片段 / 删除片段」分段控件位于工具栏最左；删除模式隐藏「极速 / 精确」组与实际入点提示，页脚徽标恒「无损」、导出按钮文案「导出保留部分」；`Delete`/`Backspace` 按**当前模式**删各自列表的最后一条；换素材（`loadFile`）同时清 `marks`——删除列表是 per-file 状态，否则标记会落到新文件的错误区间上；
- `components/CutEditor`：新增 `RemovalList`（行 = `删除 N · 标记 a→b · 实际删除 a→K · 延伸 x.xxs · 时长 · ✕`，点击行 seek 到标记起点）。实际范围由 `utils/removal.ts::actualRemovalOf` 给出，**组件不复制判定逻辑**；

## 20.4 导出接线（`M15-3`）

**落地记录（`M15-3`，2026-09-28）**：

1. **payload 与校验共用一份**：页面新增 `removalItems`（`useMemo<PipelineItem[]>`，同源 / 无变换 / `segment` = 各保留段），`startRemovalExport` 与 `checkPipeline` 都读它——**不各拼一遍 payload**（`T-005` 的收敛口径）；
2. **无损性校验 + 徽标**：`removalItems` 变化后防抖 400ms 调 `checkPipeline`；`allLossless` ⇒ 保留段汇总里显示「✓ 全程无损（同源、无变换 ⇒ 全部 stream copy）」；报出需重编码的段 ⇒ 列出 `warnings` + 各段 `reasons`，页脚徽标从「无损」改「重编码」（`lossless` 派生值同时供徽标与文案用）；校验失败显示错误、未出结果时显示"正在校验无损性…"；
3. **扩展名预判的裁决**：成品名仍取**源文件的扩展名**（`<源名>_trimmed<源扩展名>`），**不在前端复制"容器 → 扩展名"的映射**——那张表的真源在 Rust（`fs.rs::with_container_ext` / `source_container_ext`，`R4-6`/`ADR-033`），前端复制一份就是新造一处会漂移的双写（与 `T-005` 的收敛方向相反）；且本任务的前提是"后端零改动"，不宜为预判新增 Tauri 命令。**披露**：源扩展名与实际容器不符时（如把 mkv 改名成 .mp4），界面显示的名字会与后端校正后的落盘名不一致——该缺口是 `HANDOFF.md` 未决项「界面显示的输出名 vs 实际落盘名」的既有范围，随 `M14-3`（合并/工作台默认命名口径）统一处理，本批**不额外承诺**。

1. `planRemoval` 得 `keeps` → 映射为 `PipelineItem[]`：`input` = 当前源路径、`segment` = 每段、`rotateDeg: 0`、`hflip/vflip: false`、`crop: null`、`outWidth/outHeight: null`；
2. `services/tauri.ts::checkPipeline(items)` → 页脚显示「✓ 全程无损」（规则 A 下必然全 copy，这一步是**校验 + 徽标**，不做静默假设）；
3. 命名：`<源文件名>`（去扩展名）+ `_trimmed` + **跟随源容器的扩展名**（全 copy ⇒ 按 `ADR-033` 跟随源）→ `utils/paths.ts::resolveUniqueTarget` 防覆盖（决策 #19：**同名才追加时间戳**，不静默覆盖）；
4. `submitTask({ type: "pipeline", items, output, quality: settings.quality, encoder: ... })` → 现有进度/取消/任务面板全部复用；磁盘预检由 pipeline 作业体自带（估算 = 2 × Σ 片段源大小，N 段同源会偏保守，可接受）；
5. **不做**：`label` 保持后端硬编码文案（`D6` 接受"工作台 N 个片段 → 名字"的措辞）；中间件扩展名保持 `.mp4`（`D7` 接受既有缺口，源为 mkv + VP9/Opus 这类 mp4 不容纳的组合时 copy 会失败——**UI 不额外承诺，失败走既有错误路径**）。

## 20.6 风险与披露

| 风险 | 影响 | 对策 / 披露 |
| --- | --- | --- |
| 关键帧稀疏（如 10s GOP） | 每个删除区间多删最多一个 GOP | 列表逐条显示**实际删除范围与延伸量**（NFR-004 口径）；精确边界归 `CAND-022` |
| 关键帧索引未就绪/扫描失败 | 边界算不出 | 导出**禁用** + 明确提示（宁可不导出，也不产出"删不干净"的成品） |
| 中间件固定 `.mp4` | mkv + VP9/Opus 类源 copy 失败 | 既有缺口（`HANDOFF` 未决项），本批不动、不额外承诺（`D7`） |
| 任务面板/历史显示为"工作台" | 措辞不符来源 | `D6` 接受；若要改是后端 1 行文案（另开） |
| 不动点迭代写出死循环 | 页面卡死 | 迭代步数上限 = `removals.length + 1`（每轮至少并回一段删除区间，数量单调不增），超限直接返回 `nothing-left` 并记 debug 日志 |
| 大文件多段（N 段 = N 个中间文件） | 磁盘峰值 ≈ 2 × N × 源大小 | 沿用 pipeline 既有预检；空间不足在作业体内失败，不留半成品 |
