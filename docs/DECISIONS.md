| ADR-033 | **输出容器与扩展名口径统一**：以"产物容器由命令决定、最终文件名必须与之一致"为唯一口径 —— ① **copy 类**（剪切 / 无损合并 / 元数据旋转）容器 = **源容器**，扩展名跟随源文件；② **重编码类**（精确剪切 / 自动统一后合并 / 旋转转码 / 局部放大 / 工作台 pipeline 归一化）容器统一 **mp4**，扩展名固定 `.mp4`；③ 最终输出名按上述规则**生成或校正**，禁止出现扩展名与封装不符；④ `.part` 半成品与最终产物**共用同一容器规则** | ① copy 无法更换容器，跟随源是唯一的无损选择；② 重编码统一 mp4 兼容性最好（WebView2 与常见播放器无忧）；③ 现有实现"cut 跟随源扩展名、其余硬编码 mp4"一半一半，用户命名成 `.mkv`/`.mov` 时会出现名实不符；④ 半成品与成品同规则可省掉二次判断。来源：[archive/code-review-2026-09-19.md](./archive/code-review-2026-09-19.md) §4.5，实施见 PLAN `R4-6` | 生效 |
| ADR-034 | **发布版保留 `panic = "unwind"`，不采用 Tauri 体积建议里的 `panic = "abort"`**：任务作业体的 panic 必须能被 `catch_unwind` 收敛成"该任务失败"（`BUG-001` / PLAN `R4-1`），而不是让整个应用随一次内部错误退出 | `[profile.release]` 原先照 Tauri 体积优化建议设了 `panic = "abort"`，这会让 `catch_unwind` 在**发布版直接失效**——同为 panic，dev/test 下收敛为"该任务失败、队列继续"，打包后却变成"整个程序退出"，后者对用户严重得多。代价是 unwind 表带来的体积增量（**尚未实测**，需要时可对两个 profile 各跑一次 `cargo build --release` 对比）。**影响范围**：release 下任何 panic 的处置都由 abort 变为 unwind，不只是任务线程 | 生效（2026-09-21） |
