## TC-030 导入、信息面板与关键帧索引

- **覆盖**：FR-310 · FR-311 · FR-312 · FR-313 → AC-311-1 · AC-312-1 · AC-313-1
- **关联缺陷**：**BUG-008**（关键帧列表丢项）
- **夹具**：`video/极乐净土 1080p ultra.mp4`（1GB，GOP 不均、含 10s 长 GOP）；对照用 `video/123.mp4`

### 步骤

1. 剪切页 → 「打开视频文件」→ 原生对话框用 `uitool.exe type` 输绝对路径 + `key ENTER`。
2. `cdp.js eval` 读信息面板文本（编码/分辨率/帧率/音频/码率/体积）。
3. 独立跑 ffprobe 取同一文件的事实值。
4. 从界面读关键帧刻度数量；再独立跑 `ffprobe -select_streams v:0 -skip_frame nokey -show_entries frame=pts_time -of csv=p=0` 取原始行数。

### 断言

- 信息面板每一行与独立 ffprobe 事实一致（分辨率/帧率/编码/音频采样率与声道）。
- **关键帧条数 == ffprobe 原始行数**（不得丢行）。
- 若源首帧即关键帧，则列表首项 == `0.0`。
- 关键帧时间点严格升序。

### 现状

⏳ **代码已修，真机待复跑（2026-09-21）**——原现象（2026-09-19 首跑）见 [BUG-008](../BUGS.md)：`极乐净土` ffprobe 67 行 → 解析 66 条（丢了 `0.0`，列表首项变成 5.883），`123.mp4` 5 行 → 4 条（丢了 5.753333）。
根因：ffprobe 对**部分**帧会多输出一个空 CSV 字段（`0.000000,` / `5.753333,`），解析器按整行 `parse::<f64>()` 处理，这类行被静默丢弃。
修法（2026-09-21，PLAN `R4-8`）：`parse_keyframes` 改为只取行内**首个逗号前**的字段再 parse；已补 2 条解析单测锁住这两类行。**本条用例的真机复跑（刻度条数 == ffprobe 原始行数、首项 `0.0`、严格升序）待发起**。

## TC-031 极速剪切：吸附落点与产物时长必须等于界面承诺

- **覆盖**：FR-320 · FR-325 → AC-321-1 · AC-325-1；**NFR-004（所见即所得）**
- **关联缺陷**：**BUG-007**（吸附值取整后落到关键帧之前）· **BUG-009**（界面不展示真实落点）
- **夹具**：`video/merge_test_a.mp4`（关键帧 0.052667 / 1.319333 / 9.786 / 14.052667 / 15.619333，**均为非整毫秒**）

### 步骤

1. 剪切页打开 `merge_test_a.mp4`，确认「入点吸附关键帧」开关为开（默认开）。
2. 把入点手柄拖到关键帧刻度附近（本例 x≈98 对应 1.319333s）→ 读界面「开始」输入框的值。
3. 拖出点手柄到目标时刻 → 读「结束」输入框的值。
4. 点「添加片段」→ 读片段卡上的区间与时长。
5. 点「开始剪切」→ 等任务终态 → 用 ffprobe 核验产物。

### 断言（本用例的核心）

- 产物的**首个视频 `pts_time` **等于界面显示的入点（容差 ≤0.1s）。这是"真实落点"的硬口径——`-ss` 落在关键帧之前时 ffmpeg 会退到**上一个**关键帧，pts 会直接暴露。
- 产物 `format.duration` 等于界面片段卡上的时长（copy 链路容差：≤0.35s）。
- 流数量与 `codec_name` 与源一致（极速剪切是 stream copy，**不得重编码**）。
- 全帧可解码；**在产物首帧附近再解 1s**，确认起点画面正常。

### 现状

✅ **通过（2026-09-21 真机复验）**——同一条操作路径，修复前后对比（PLAN `R4-8`）：

| | 界面 | 修复前产物 | 修复后产物 |
| --- | --- | --- | --- |
| 区间 | `00:00:01.319` → `00:00:03.995` | — | — |
| 时长 | **2.7s** | **4.036s**（偏长 1.36s / 51%）❌ | **2.756s** ✅ |
| 首个视频 pts | — | **0.052667**（= 上一个关键帧）❌ | **0.039333** ✅（关键帧只有一个，正是吸附目标） |
| 流与编码 | — | h264 + aac 原样 copy | h264 + aac 原样 copy ✅ |

原 ❌ 现象与根因（2026-09-19 首跑，见 [BUG-007](../BUGS.md)）：`list_keyframes` 给 `1.319333` → `Timeline` 吸附 → 界面显示 `00:00:01.319` → 参数构建器把 `-ss` 格式化成三位小数得 `1.319`，**比真实 pts 小 0.33 毫秒** → ffmpeg 退到上一个关键帧；关键帧越稀疏偏长越大（`极乐净土` 实测最大 GOP 10s）。修法：输入侧 `-ss` 改走 `fmt_seek`（+1µs、6 位小数），输出侧不变。

同批修复的 [BUG-009](../BUGS.md) 也在本条路径上确认：入点拖到不吸附位置时，界面出现「实际入点 `00:00:01.319`」提示，时间轴落点虚线（x=99）正落在关键帧 `1.319333` 上。

证据产物：`video/` 下的 `merge_test_a_part_001_20260921_004928.mp4`（修复后，13.6MB）与 `merge_test_a_part_001.mp4`（修复前，21.8MB）——临时证据文件，随夹具目录一起不入库。

**命令级对照（2026-09-21，同一夹具，`-t 2.676` 固定）**——用于回答"入点**不**落在关键帧上时，界面按实际落点算的时长还准不准"：

| 输入侧 `-ss` | 实际落点 | 产物时长 | 首个视频 pts |
| --- | --- | --- | --- |
| `1.319`（修复前的三位小数） | `0.052667`（退到上一个关键帧） | **4.036s** | `0.052667` |
| `1.319334`（`fmt_seek`，吸附到 `1.319333`） | `1.319333` | **2.756s** | `0.039333` |
| `2.000001`（`fmt_seek`，**非吸附**入点） | `1.319333` | **3.439s** | `0.039333` |

第三行是重点：请求区间 `[2.000, 4.676]`、实际落点 `1.319333`，界面按"落点→出点"显示 **3.357s**，产物 **3.439s**，差 0.08s（与第二行同源的尾部/音频 priming 偏移），在 §4 口径的 0.35s 容差内。
结论：copy 路径的前导段是**保留**的（内容跨度 = `[实际落点, 出点]`，不是 `[实际落点, 实际落点+请求时长]`），所以"按实际落点算时长"在非吸附场景同样成立，与 `-t` 从哪个时刻起算无关。

## TC-032 精确剪切：帧级落点与时长

- **覆盖**：FR-322 → AC-322-1
- **夹具**：`video/123.mp4`（平均帧率 24000/401，非整帧率，是专门挑来打精确落点的）

### 步骤

1. 剪切页打开 `123.mp4`，模式切「精确」。
2. 入点设 `2.000`、出点设 `5.000`（用数字输入框：坐标点击 + `ctrl+a` + 键入 + Enter）。
3. 「添加片段」→「开始剪切」。
4. ffprobe 核验。

### 断言

- 产物时长 `3.000 ± 0.2s`（精确模式是重编码，**必须明显优于极速模式的 GOP 量级误差**）。
- 音频流保留（精确剪切音频走 copy）。
- 分辨率与源一致，全帧可解码。

### 现状

✅ **通过（2026-09-19，命令级等价验证）**：3.0±0.2s、音频保留、全帧可解码。真机复跑待补。

## TC-033 多片段、区间编辑与输出命名

- **覆盖**：FR-323 · FR-324 → AC-323-1 · AC-324-1
- **夹具**：任一夹具 + 目标目录已有同名产物

### 步骤

1. 同一文件剪出 2 个片段（不同区间），确认片段列表按添加顺序排列。
2. 删掉最近添加的一个（`Delete` 快捷键），确认移除的是最后一个。
3. 用数字输入框把入点改到出点之后 → 确认「添加片段」被禁用（不得提交非法区间）。
4. 导出到已存在同名产物的目录，再导出一次 → 检查命名策略。

### 断言

- 片段顺序 == 添加顺序；删除行为符合"删最近添加"。
- `结束 - 开始 < 0.1s` 时「添加片段」为 `disabled`（直接读 DOM 的 `disabled` 属性，别靠肉眼）。
- **同名才追加**：目录里已存在 `X.mp4` 时新产物不得静默覆盖（决策 #19）。
- 产物数量与片段数量一致，文件名为规格模板。
