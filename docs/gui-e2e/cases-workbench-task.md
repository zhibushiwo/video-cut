## TC-037 工作台：多素材多片段 → 合成导出

- **覆盖**：FR-380 → AC-380-1（组级）
- **夹具**：`video/merge_test_a.mp4` + `video/merge_test_b.mp4`（同参数）；可选 `video/极乐净土 1080p ultra.mp4`（长片）

### 步骤

1. 工作台「添加视频素材」加入两个素材（逐个走原生对话框）。
2. 点素材卡进剪切视图 → 各剪出 1–2 个片段（其中至少一个片段带旋转、一个带局部放大）→ 片段池应出现对应卡片。
3. 把片段加入时间轴（点「+」或拖卡片过去）。
4. 拖动时间轴上的块改变顺序 → 记录新顺序。
5. 成品预览连播一遍，并在中间 seek 一次。
6. 「合成导出」→ 等终态 → ffprobe 核验。

### 断言

- 成品 `format.duration` **等于各片段时长之和**（±0.6s）；分辨率统一为基准片段的分辨率；音频流保留。
- **接缝可播**：在每个片段边界前后各取 1s 解码一遍（走重编码+normalize 的片段必须已对齐 timescale，否则第二段起时间戳会坏）。
- 时间轴拖拽后**导出顺序 == 时间轴顺序**（顺序只在时间轴上表达）。
- 切换素材/片段时**无残留**：进度条、出入点、关键帧状态全部重建；切回来不应看到上一个素材的选区（M9-2 的口径）。
- 成品预览能连播、能 seek（不是只播第一段）。

### 现状

✅ **链路通过（2026-09-19，命令级等价验证）**：copy 片段 + 转码片段（180° + 裁剪放大 + timescale 对齐）→ normalize → concat，片段合计 9.044s == 成品 9.044s，全帧可解码，接缝窗口通过。
⏳ 界面侧（素材卡/片段池/时间轴拖拽/成品连播）待真机复跑。

## TC-038 任务系统：并发、取消、终态与历史落盘

- **覆盖**：FR-360 · FR-361 · FR-362 → AC-360-1 · AC-361-1 · AC-362-1；NFR-006–009
- **关联缺陷**：BUG-001（作业体 panic 泄漏并发槽）· BUG-002（输出替换原子性）

### 步骤

1. 连续提交 3 个耗时任务（例如对 1GB 源做 3 次不同区间的极速剪切）→ 观察面板并发数。
2. 对**运行中**的第 1 个任务点「取消」。
3. 对**排队中**的第 3 个任务点「取消」。
4. 展开面板，逐条核对终态、进度、日志。
5. 检查输出目录与 `%APPDATA%\com.hippo.video-cut\history.json`。

### 断言

- **并发上限 2**：第 3 个任务处于排队态，不得同时跑 3 个。
- 取消运行中任务 → 终态 `cancelled`，进程被 kill，**不留 `.part.<令牌>` 半成品**，且**不产出**残缺产物。
- 取消排队中任务 → 终态 `cancelled`，**作业体不执行**（由此该任务的簿记回收必须走清理钩子，写在作业体里的回收会被跳过）。
- 进度单调不倒退；终态后进度停在 100% 或取消点，不再刷新。
- 每个终态（完成/失败/取消）都**恰好一条**历史记录落进 `history.json`，含 `kind`、`label`、`outputs`、`finishedAt`；失败记录必须带 `error`。
- 失败路径**不吞删除错误**：目标被占用时旧文件不得丢，错误信息需含 `.part` 完整路径（BUG-002 的回归口径）。

### 现状

⏳ **待跑**。状态机与清理钩子已有单测覆盖（见 [TESTING.md](../TESTING.md) §3.1 的 TC-004），本用例补的是**真机 GUI + 落盘**侧的端到端确认。

## TC-044 成品连播跨片段边界（`BUG-014` 回归）

- **覆盖**：AC-380-1（成品预览连播）· `BUG-014`
- **夹具**：`video/merge_test_a.mp4`（20.1s）+ `video/merge_test_b.mp4`（23.0s）
- **前置**：按 [README.md](./README.md) §2.2 起应用；**每步驱动前先 `{"focus":"video-cut"}`**——被遮挡窗口的 rAF 停摆会把"后台节流"误判成"连播停住"

### 步骤

1. 工作台「添加素材」加入两个夹具（逐个走原生对话框，`uitool type <绝对路径>` + `uitool key ENTER`）。
2. 点素材卡 A 进剪切视图 → 设出点 10s → 「添加为片段」（重复一次以得到**同源相邻**两段）；点素材卡 B → 同样剪一段 → 时间轴共 3 段，含**同源相邻**（A→A）与**跨源**（A→B）两种边界。每次「添加为片段」都会同时入轴。
3. 切「成品预览」→ 先**复位到 0**（把 `aria-label="成品播放进度"` 的 range 用 `value` 原生 setter 置 0 并派发 `input`）→ `{focus}` → 点「播放」。
4. 页面内高频采样（`setInterval` 20ms + 仅记录"变化"）：两个 `<video>` 的 `paused`/`currentTime`/`src`、播放/暂停按钮文案、进度区读数（**取 `aria-label` 为「成品播放进度」的 range 的父级文本**，不要用 `body.innerText` 正则——页面上不止一处 `mm:ss / mm:ss`）。
5. 观察跨过第一处边界（10s）与第二处（20s）后是否仍在推进。
6. 拖进度条 seek 到 38s → 点播放 → 观察是否继续推进。
7. 让它播到末尾（槽内 `currentTime` 到 `duration`）→ 观察是否正常停止。
8. 复位到 0 → 播放约 4s → 点「暂停」→ 核对读数与 `<video>.currentTime` 对齐。

### 断言

- **跨段不停**：每一处边界后活动槽的 `currentTime` 持续增长；期间播放/暂停按钮**始终是「暂停」**（不得回落到「播放」）。
- **槽轮换**：边界处活动槽在 a/b 间切换，且新活动槽立刻开始推进（有 `play` 生效），离场槽停在出点附近。
- **seek 后继续**：seek 到 38s（落在第 3 段内）后按播放，`currentTime` 从映射位置（38 − productStart）继续增长。
- **末尾正常停止**：活动槽走到 `duration` 后，按钮变「播放」、读数 = 总时长，**不早停**（此前停在第 1 段末尾即 `00:00:10`）。
- **暂停对齐**：暂停后读数 ≈ 该槽 `currentTime` 对应的成品时间（± 1 帧量级）。

### 现状

❌ **修复前（2026-10-05 首跑复现）**：停在第一处边界——20ms 内 `btn 暂停→播放`、新活动槽 `paused`、rAF 空转；读数固定 `00:00:10`（= 第 1 段末尾）。
✅ **修复后（2026-10-05）**：3 段连续跨过 10s / 20s 两处边界不停（`btn` 恒为「暂停」、活动槽持续推进）；seek 38s 后继续播；末尾正常停止（读数 = 总时长）；暂停后读数 = `00:00:04`（对齐实际位置）。根因与修法见 [BUGS.md](../BUGS.md) `BUG-014`（`onPause` 的活动槽判定误用 React state `slot`，改读 `slotRef`）。

### 复现/验证要点（供下次复用）

- 断言优先读 **`<video>` 元素状态 + 按钮文案**，它们比读数可靠（读数是 M11-3 的**离散镜像**，播放中本就不更新）。
- 想抓"谁没调 `play`"，可运行时包一层 `HTMLMediaElement.prototype.play/pause` 记录调用与 `Error().stack`——本次正是靠它把 `onPause` 的误判钉死的。
- `value` 原生 setter + `input` 事件能改受控 range；但**文本输入框**用合成事件改不动 React state（提交时仍是旧值），改文本字段要走真实键鼠（`cdp.js mouse/key/type`）并**先 focus**。

## TC-048 渲染即预览（`M12-2`）

- **覆盖**：`FR-1760`（自动渲染真实成品并播放）· `FR-1761`（回退与手动精确预览）· `FR-1762`（任务隔离与缓存）
- **夹具**：`video/merge_test_a.mp4` + `video/merge_test_b.mp4`（同参数，可无损 concat）
- **前置**：按 [README.md](./README.md) §2.2 起应用（dev 构建 + CDP）；每步驱动前先 `{"focus":"video-cut"}`
- **缓存目录**：`%LOCALAPPDATA%\com.hippo.video-cut\cache\preview\`（`app_cache_dir`）

### 步骤

1. 工作台加两个夹具 → 各剪一段（**不加旋转/放大/裁剪**）→ 时间轴 2 段，页脚检测汇总应为 **✓ 全程无损**。
2. 停手约 2s（`waitFor` 页脚出现「渲染预览中…」→「渲染预览就绪」，超时按 15s 给）。
3. 断言预览区**只有一个 `<video>`** 且其 `src` 指向 `cache/preview/*.mp4`（不是源文件）：
   `[...document.querySelectorAll("video")].length === 1` 且 `src.includes("/preview/")`。
4. 播放一次：跨片段边界**不停顿**（本用例只有 2 段，重点看第 1 段末尾不回落「播放」）；播到末尾正常停止。
5. 编辑时间轴（`C` 切割 / 拖动块重排）→ 观察旧 preview 文件被取代：`cache/preview/` 下**只剩一个** `.mp4`（`read_dir` 计数），且预览在新渲染就绪后继续可播。
6. **重编码回退**：给某片段加旋转（非恒等）→ 页脚汇总变 ⚠ → 断言**不出现**「渲染预览中…」，预览区回到双 `<video>` 虚拟连播，提示条写明"含重编码片段，已回退近似预览"。
7. **手动精确预览**：点页脚「精确预览」→ 出现「渲染预览中…」→ 就绪后预览区回到单文件分支。
8. **任务隔离**：全程断言任务面板（`TaskProgress`）**行数不因预览变化**；同时手动点「合成导出」→ 导出正常完成且**恰好一条**历史记录（预览不产生历史）。
9. **缓存**：设置页缓存统计的「渲染预览」占用 > 0；点「清理缓存」后回 0，且 `cache/preview/` 为空。

### 断言（量化）

- 预览 `<video>` 的 `src` **命中缓存目录**（而非任何源文件路径）。
- 预览产物的 `format.duration` == 各片段时长之和（±0.5s，可用 `ffprobe` 复核缓存文件）。
- 跨片段边界处**播放按钮恒为「暂停」**（不得回落到「播放」）。
- 预览渲染期间**任务面板无新增行**；历史条数不增加。
- `cache/preview/` 里 `.mp4` 数量恒为 **1**（新编辑取代旧文件）。

### 现状

🔄 **真机半部分通过（2026-10-05 首跑）**——**已验**：纯无损 2 段时间线自动渲染出真实成品（`preview/<令牌>.mp4`，`format.duration` 43.1s = 20.1+23.0），预览区只剩 **1 个 `<video>`** 且 `src` 命中缓存目录（非任何源文件）；两次自动渲染后 `preview/` 里**只留 1 个 mp4**（旧令牌被清扫）；跨 concat 接缝（20.1s）连续推进、无回退无停顿（6s 采样异常 0）；播到末尾正常停止且读数 = 总时长；暂停后可继续。**首跑抓出一个真缺陷并已修**：渲染分支下进度条 seek 不走 `seekInternal`（那是"成品内↔源内"的双槽映射），改为直接改成品 `<video>.currentTime`。**第二跑（2026-10-05，放大/裁剪构造重编码）**——**已验**：裁剪 800×600 后检测转「⚠ 1 个片段需重编码」；**不自动渲染**（日志无预览提交）；预览回退到源文件（`<video>` 的 `src` = 源路径，非缓存）；提示条写明「时间线含重编码片段，已回退近似预览（可点页脚「精确预览」渲染真实成品）」→ `AC-1761-1` 的**抑制与回退半通过**。点「精确预览」→ 页脚转「渲染预览中…」→ 47s 后任务完成、新预览文件落盘且**旧文件被清扫**（`preview/` 仍只有 1 个 mp4）→ **`AC-1762-1` 的"只留当前一份"再获证实**。
❌ **第二跑抓出两个真缺陷（第二个待修）**：① 进度条 seek 在渲染分支失效（已修，见下）；② **渲染任务完成后事件未被采纳**——页脚永久停在「渲染预览中…」、`renderedSrc` 不切换（预览仍播源文件），且因 `canRenderNow` 依赖 `phase` 而把「精确预览」**永久置灰**（回退路径没有出口，直接违背 `FR-1761`）。已做**兜底缓解**（见下）。
**第三跑（2026-10-05，装诊断后专测定案）——缺陷②复现失败，且"与耗时相关"的假设被证伪**：同一条慢路径（裁剪 → 手动「精确预览」）这次**完全正常**——55s 后预览切到重编码产物 `preview/ad3831b6e3558b84-0001.mp4`；日志留痕为 `pid=… tid=… match=true status=completed outputs=1`（另一次无损快路径同样 `match=true outputs=1`）。**结论：缺陷②是间歇性的，与任务耗时无关**（原先"快能慢不能"的判断作废，已在本行更正）。失败样本仍**未被捕获**，故"事件根本没到" vs "到了但落到旧实例"**仍未分流**；诊断留痕（无条件记录终态事件的 pid/tid/match/outputs）已在位，下次复现即可一锤定音。
**自动半已就绪**：`previewRender` 9 条 Vitest（无损才自动渲染 / 同签名不重复提交 / 同签名失败不自动重试 / 签名一变立刻回落）· `task/manager.rs` 7 条单测（优先级优先挑选、低优先级不饿死、同 key 复用、异 key 取代、取代后新登记存活、排队中取代不跑作业体、internal 的 pipeline 任务不进 snapshot）· e2e `preview_pipeline_full_chain`（copy+重编码 → normalize → concat 落预览目录，断言时长/可解码/容器 mp4）· `pipeline.rs` 单测 `sweep_preview_dir_keeps_only_current_token`（只留当前令牌）。
